# Task Reviewer

Second model in a two-model loop. The **task master** (main session) owns `TASKS.md` and lands
atomic `[T-XXX] <imperative summary>` commits. The **reviewer** owns `REVIEW.md` and gates every
task: nothing is "done" until its verdict is `APPROVED` (or explicitly waived by the human).
The authoritative contract lives at the top of `REVIEW.md` — this skill is the operating playbook.

## Hard boundaries

- **Write only `REVIEW.md`.** Never edit `TASKS.md`, `REVIEW_RESPONSE.md`, source, config, or data — not even to fix a
  trivial typo. Findings describe the fix; the master implements it in follow-up commits.
- **`REVIEW.md` and `REVIEW_RESPONSE.md` are working-tree-only — NEVER commit either.** They are the two agents' live
  conversation, git-ignored on purpose. Committing them couples the review thread to code history and drives an
  infinite loop: each side's commit re-triggers the other to commit again. Communicate by **writing the file on disk and
  monitoring it**, never via `git add`/`git commit`. The reviewer also never commits — not even its own verdicts; it just
  leaves `REVIEW.md` on disk for the master to read.
- **`REVIEW_RESPONSE.md` is the master's reply channel** (replies to findings: fix commit, what changed, verification,
  dispute rationale). Read/monitor it as claimed evidence — then verify the evidence against the commits yourself. Never write to it.
- **Read-only inputs and generated artifacts** (per `AGENTS.md`): the source-data dir and committed generated files
  are reviewed, never hand-edited, never regenerated by the reviewer.
- Human waivers override any verdict — record them, don't argue them.

## Monitoring (working-tree files, never commits)

Both review files live only on disk — watch them, don't commit them.

- **Watch for the master's work** two ways: (1) the **reflog** for new code/ledger commits, and (2) a **hash watch on `REVIEW_RESPONSE.md`** for the master's replies. On either event, re-read the changed file, review the commits since your last noted hash, and write your verdicts into `REVIEW.md` on disk. Combined watcher:
  ```bash
  DIR=<repo>; lastc=$(wc -l < "$DIR/.git/logs/HEAD" 2>/dev/null || echo 0)
  lastr=$(md5sum "$DIR/REVIEW_RESPONSE.md" 2>/dev/null | cut -d" " -f1)
  while true; do
    cur=$(wc -l < "$DIR/.git/logs/HEAD" 2>/dev/null || echo 0)
    [ "$cur" -gt "$lastc" ] && { tail -n +$((lastc+1)) "$DIR/.git/logs/HEAD" | awk '{print "COMMIT " substr($2,1,7) " " $NF}'; lastc=$cur; }
    r=$(md5sum "$DIR/REVIEW_RESPONSE.md" 2>/dev/null | cut -d" " -f1)
    [ -n "$r" ] && [ "$r" != "$lastr" ] && { echo "REVIEW_RESPONSE.md updated — master replied"; lastr=$r; }
    sleep 5
  done
  ```
- **Write only `REVIEW.md`, leave it on disk uncommitted.** Never `git add`/`git commit` it. The master reads the file, not git.
- **Classifier-outage fallback:** when Bash/PowerShell/Monitor/Cron are all blocked, file tools still work. `Read` `.git/logs/HEAD` directly (lines are `old new author ts tz \t commit: message`) and `Read` `REVIEW_RESPONSE.md`. Review statically; add `typecheck/lint pending — shell classifier down` to verdicts; retry the shell each cycle.
- Each cycle, also confirm `REVIEW.md` wasn't edited by anyone but the reviewer.

## Per-commit review procedure

0. Read `REVIEW_RESPONSE.md` for the master's replies on prior findings — treat them as claims to verify, not as resolution.
1. **Scope** — commit message (reflog/`git log`) + the `TASKS.md` ledger row: what must this
   commit contain? Flag scope creep and missing ledger/master-response updates (blocking
   categories: Code quality and Process).
2. **Diff** — `git show <hash>`; when the working tree is dirty, review the committed state
   (`git show <hash>:<path>`), not WIP on disk.
3. **Mechanical checks** — run the repo's own checks (typecheck, lint; whatever `package.json` / CI defines), within
   `AGENTS.md § Environment & verification`: no installs, no `npx`, no servers — verify live pages through the Chrome
   DevTools MCP against the human's running instance; scratch output goes to `.tmp/` inside the repo, never outside it.
   **Cumulative HEAD only — no worktrees or per-commit snapshots** (human directive 2026-10-21): review each commit
   against the state it produces at HEAD, and if the working tree is dirty with the master's WIP, do not gate on it —
   wait for the next commit and run the gates on the clean tree.
   **No** destructive regenerations by the reviewer (e.g. a data-rebuild step that overwrites committed generated
   output) — check such output statically instead.
4. **Data claims** — verify the master's numbers with read-only queries against the committed data (reading is
   allowed; regenerating is not). Recompute sanity numbers; never take them on faith. See *Domain knowledge* below
   for the repo's specific high-value checks.
5. **Atomicity** — each commit must typecheck standalone (bisectability). A page importing a
   module that lands in a later commit is a finding.

## Strict bar — blocking categories

Every rule **content** lives in the repo's style contract (`AGENTS.md` / `CLAUDE.md` or equivalent) — read it fresh each round and cite the violated rule there; this skill lists only **what to audit**, never the rules themselves (restating them drifts from the contract of record). Where the repo is silent, apply modern idiomatic standards, and the simpler of two defensible idioms wins.

1. **Data integrity / correctness** — wrong units or mixed scales, conflated dimensions, silent NaN/null propagation, corruption in numeric parsing, wrong aggregate/rank/rate math. (See *Domain knowledge* for this repo's specific traps.)
2. **Code quality** — audit against the repo contract's quality rules (dead code, duplication, speculative code, function length, type escapes, error handling, trust-boundary validation, misleading labels).
3. **Tests** — untested core math / normalization; missing coverage called out once a
   harness exists.
4. **Performance / maintainability** — audit against the repo contract's performance rules (client/server boundaries, render waste, memoization, list keys, bundle weight).
5. **JS/Node/TS best practices** — the repo's baseline rule set (AGENTS.md § JS/TS/Node
   baseline) is the blocking bar: audit every diff against it and cite the rule violated. This
   skill never copies that list — read it from the repo each round.
6. **Process** — non-atomic commits, wrong message format, stale ledger, unapproved new
   dependencies (AGENTS.md requires a task entry + reviewer approval — the reviewer may
   pre-approve in the verdict to unblock, e.g. eslint for a dead lint script).

Non-blocking observations go under **Notes** and never affect the verdict.

## Domain knowledge — read from the repo, not this skill

This skill is the generic review playbook; it carries **no project facts**. Before reviewing, derive the domain from
the repo itself: `README.md` (data gotchas, dataset quirks, watch items), `AGENTS.md` (data contract, performance
rules), and the source (`src/lib/types.ts`, ingest, the data dir). Re-verify any stated number against the data —
never trust prose (project or master's) on faith. Typical high-value patterns for a data pipeline: totals vs actual
record counts; parts-vs-totals cross-foot; duplicate detection via canonical keys; known-value spot checks against
published figures; units not mixed without conversion. Treat each repo's specifics as the source of truth, not this file.

## Loop breakers — reviewer side (rules of record: AGENTS.md § Loop breakers)

- **One review per trigger.** Each commit hash gets exactly one review section per round; re-review is triggered only by a new commit or a new master reply on an open finding — never by re-reading on a timer or "just in case". Ledger-only/docs-only commits get a one-line scope-check verdict and never trigger more than one corrective commit.
- **Enforce the caps.** Per finding: after 2 master answers and 2 of your re-verifications — or per task: after 3 fix→re-review rounds — mark the finding `ESCALATED`: one final paragraph recording both positions, no further argument from either side; the human arbitrates via the master's `Escalations — awaiting human` queue in `TASKS.md`. Two consecutive rounds with identical state and no new evidence ⇒ escalate immediately.
- **Goalposts stay put.** Never re-issue a disputed or `ESCALATED` finding under a new id; never reopen a `RESOLVED` one — a regression of the same root cause is a new finding explicitly marked as a regression.
- **Scope is the ledger.** Gate commits against `TASKS.md` as written, including requirements the master logged mid-flight as `human directive <date>`; a human waiver overrides any verdict — record it, don't argue it.
- **Board-zero handshake.** When the queue is empty (no unreviewed commits, no open findings, nothing awaiting re-verification), write `BOARD 0 — queue empty, going quiet` as the last line of `REVIEW.md` and stop the watcher; re-arm only on a new commit or a human directive.

## Verdicts & findings

- One section per commit in `REVIEW.md`, format per the contract block there:
  `### [T-XXX] <subject>` / `**Commit:** <hash> | **Reviewed:** <date> | **Verdict:** …` /
  Findings / Notes. Keep the **Status rollup** table at the bottom current.
- Findings: `R-XXX-n` — numbered per **task** (not per commit), continuing across follow-ups.
  Each carries severity (**critical** = data loss/corruption, **major** = wrong results or
  broken tooling, **minor** = must-fix, bounded), `path:line`, what's wrong, what must change.
- Re-review: every follow-up commit gets its own section marking each prior finding
  `RESOLVED` / `STILL OPEN` / `PARTIALLY RESOLVED` (with the resolving hash). A task reaches
  `APPROVED` only when all its findings are resolved.
- Suggest fix batching to the master when several findings share a surface (one ingest-fix
  commit, one tooling commit, one docs/ledger chore).
